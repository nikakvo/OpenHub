Welcome to OpenHub

OpenHub is a GitHub client for Android. Read and write almost everything you would on github.com: browse and search code, edit files, publish releases, review and merge pull requests, work with issues and discussions, follow builds, get notifications.

1 · getting started

Logging in

The login screen offers two ways. Both give OpenHub the same permissions.

Login with browserGitHub opens in your browser. Log in there and approve OpenHub; you come back to the app by yourself. Only shown when the build has its own GitHub OAuth App.
Sign in with tokenWorks everywhere. A personal access token is a password made only for apps. Tap Create token: GitHub opens with the right permissions already ticked. Press Generate token, copy it and paste it into OpenHub.
Your tokenIt is stored only on this phone, encrypted, and sent only to GitHub's API. You can revoke it any time on github.com. More in Privacy.

More than one account

Open the side menu, tap the round arrow next to your name and choose Add account. Tap an account in the same list to switch to it. Logout removes the current account from the phone. The arrow is in the side menu of every screen; there it opens a small menu with the same choices, so you stay where you are.

First steps

  1. Open the side menu (top left) and look around: your repositories, notifications, trending projects.
  2. Open any repository. The Info tab shows its README, Files its code.
  3. Tap the ⋮ menu of a repository: releases, Actions, pull requests and more are there.
  4. Pull any page down to load it again from GitHub.
  5. Not sure what a word means? See the Glossary.

The numbers on Info

Issues and Pulls open the issue and pull request lists (they count only open ones). Stargazers, Forks and Watchers show who starred, forked or watches it.

NoteSince July 2026 GitHub shows stargazers and watchers only to the repository's owners and collaborators. For other repositories you see a note instead of the list. Not a bug.

Forks: Sync fork and Contribute

In a fork, Info shows how the branch you look at stands against the original repository, like github.com: This branch is 4 commits ahead of and 8 commits behind owner/repo:main. The numbers come from GitHub each time the page loads or you pull down. Tap ahead for your own commits, behind for the new commits of the original, and the name to open the original repository. The default branch of a fork is compared with the default branch of the original, any other branch with the branch of the same name.

If you can push to the fork, two buttons follow:

  • Sync fork (filled when there are new commits): Update branch brings the new commits into your branch. Without commits of your own the branch simply moves forward; with commits of your own GitHub keeps them and adds a merge commit. Discard N commits makes your branch exactly like the original and removes your own commits from it (it asks again first). If both changed the same lines, GitHub cannot merge by itself: Open on github.com opens the page where a pull request can resolve the conflicts, or discard your commits.
  • After a sync the page reloads from GitHub and Open Actions takes you to the workflows, for example to start a build of the updated fork.
  • Workflows of a new fork: GitHub keeps them off until they are turned on once, and allows that only on github.com: until then GitHub does not even list them, and no app can turn them on. Info then says how many workflow files the fork has and shows Turn on on github.com (the dialog after a sync offers it too). It opens the fork's Actions page in the browser; tap I understand my workflows, go ahead and enable them there and come back: Info asks GitHub again. Workflows that GitHub reports as Disabled in this fork get Enable workflows instead, which the app can do itself; afterwards it says how many GitHub reports as active. One workflow at a time: Actions menu → Workflows (13).
  • Contribute: with commits of your own, Open pull request starts a pull request into the original repository.

Top buttons

Star (like or save it) and Branches or tags (switch the branch you look at; files, commits and README follow it).

4 · files: add, edit, upload, history

In repositories where you can write, the Files tab works like github.com. Every change is a real commit with your name.

Adding

  • The + button: Create new file (type a / in the name to make folders, e.g. docs/notes.md) or Upload files from the phone into the folder you are in.
  • Several uploaded files become one commit. Files up to 25 MB; bigger files belong in a release.

Changing

  • A submodule (link icon, "submodule" instead of a size) opens the repository it points to, at the commit this repository uses.
  • Long-press a file: Edit file, Rename or move, Delete file, Download. An open file has the same actions in its toolbar (pencil) and menu.
  • A code file opens at a readable font size. Its menu has Wrap lines: on, long lines go on below at the screen width, next to their line number; off, they stay whole and the page scrolls sideways. The choice is remembered.
  • The editor shows the file in a monospace font; Markdown files also get Write and Preview. Text files up to 512 KB can be edited.
  • At the bottom: Branch: main ▾. Tap it to commit to another branch; an open file is then loaded again from that branch.

History and blame

  • Everyone can do this, also in other people's repositories. Long-press a file (or open it and use the menu): History lists the commits that changed it, newest first, on the branch you are looking at; tap one to see what it changed. Long-press a folder for the history of everything inside it.
  • Blame shows the file with the commit that last changed each group of lines above it: message, short SHA, who and when. The colored bar on the left is the age: orange for the newest changes of the file, grey for the oldest. Tap a commit line to open the commit; long-press it for Copy SHA. The menu has History and Open in browser.
  • History follows the path: a file that was renamed shows its commits since the rename only. Pictures have no Blame item, and other binary files show a note instead.

Commit changes

Asks for a short message (prefilled, e.g. Update README.md) and an optional longer description, then where the commit goes:

Commit directly to the branchThe change lands right away. On a branch that is not the default one, Start a pull request into main is offered too; if the branch already has an open pull request, the commit goes into it and it opens.
Create a new branchThe change goes into a new branch (name prefilled), and with Start a pull request ticked a pull request opens right after. The safe way for important changes.
edit a file → commit to a new branch → pull request → review → merge into main
Good to knowFile permissions such as executable scripts are kept. Changing files under .github/workflows needs the workflow permission; tokens made with Create token in this version have it.
5 · branches, protection and rulesets

A branch is a separate line of work: you change things there without touching main, then merge them with a pull request.

Branches (repository menu) lists all branches; the default and protected ones are marked. Tap a branch and choose Browse files to open its files, or Compare with the default branch.

Compare (repository menu) shows how one branch or tag differs from another: how many commits it is ahead and behind, its commits (tap to list them) and the changed files with their diffs (tap a file). Tap Base or Compare to choose, Swap base and compare to turn it round. With write access and two branches, Open a pull request starts one with both already chosen.

  • + creates a branch. With one branch it asks for the name right away; with more, you pick the branch to start from first.
  • Tap a branch to rename or delete it.
  • Admins also get Branch protection: require a pull request (with a number of approvals), conversation resolution, linear history, allow or forbid force pushes and deletions, and apply the rules to admins too.
  • Rules for this branch lists every rule of the rulesets that applies to the branch, and which ruleset it comes from.
Watch outWithout Apply the rules to administrators too you, as the owner, can still commit directly to a protected branch. Protecting branches of private repositories needs a paid GitHub plan.

Rulesets

A ruleset is GitHub's newer way to protect branches and tags. One ruleset can cover many branches (by name or pattern), can be switched off without losing its settings, and has a bypass list of who may ignore it. Rulesets and classic branch protection work together; when both apply, the stricter rule wins.

Open them with Rulesets in the ⋮ menu of Branches, or in the repository Settings. Everybody can look at them; admins can change them.

  • + makes a new branch ruleset or tag ruleset. Tap a ruleset to edit it; long-press it to Switch on / Switch off or Delete it.
  • Target branches: one name or pattern per line, e.g. main, release/*. Default branch adds ~DEFAULT_BRANCH, All branches adds ~ALL. Exclude takes branches out again.
  • Bypass list: Repository admins may bypass these rules, Always or Only through pull requests (tag rulesets have only Always, so there is no choice to make). Other actors set on github.com are kept.
  • Rules: restrict creations, updates and deletions, require linear history, signed commits, a pull request (approvals, dismiss stale approvals, code owners, approval of the latest push, resolved conversations, allowed merge methods), status checks (by name, optionally up to date), and block force pushes. Tag rulesets offer the rules that apply to tags.
  • Rules OpenHub does not edit (merge queue, code scanning, workflows, name patterns, push rulesets and others) are named under the rules and kept exactly as they are when you save.
  • ⋮ → History lists the versions of a ruleset. Tap an older one to load it into the form; Save restores it.
  • In Branch protection of a protected branch, Convert to ruleset opens a new ruleset with the same rules. Nothing is saved until you press Save; the classic protection stays until you remove it.
  • Rulesets of the organization show "from" and the organization's name; they can only be changed there.
  • A blocked pull request shows the rules of its base branch in the merge box (pull requests).
PlansRulesets are free for public repositories. For private ones GitHub needs a paid plan and answers with a message saying so. "Evaluate" (rules that only report) is an Enterprise feature; OpenHub offers Active and Disabled.

Deploy keys

A deploy key is an SSH key that gives one server, device or script access to this one repository, without your account: for example a build server, a backup job or Termux on another phone. Deploy keys in the repository settings (under Rulesets) lists them, like github.com.

  • Each row shows the key's title, its fingerprint (SHA256:…, the same as ssh-keygen -lf key.pub prints), Read-only or Read and write, when and by whom it was added and when it was last used.
  • + adds a key: paste the public key (one line starting with ssh-ed25519, ssh-rsa or ecdsa-sha2-) or tap Choose a .pub file. The fingerprint appears while you type, so you can compare it with the one on the other device. Without a title, the key's comment is used. Allow write access lets the key push too; leave it off when the key only needs to download.
  • Only the public key (the file ending in .pub) goes to GitHub. A private key is recognized and refused on the phone, before anything is sent.
  • Tap a key: Copy fingerprint, Copy public key, Delete key. GitHub does not let a key be changed: delete it and add it again. Whatever uses a deleted key loses access at once.

Webhooks

A webhook makes GitHub send a message to a web address whenever something happens in the repository, for example a push or a new issue: a chat bot, a build server or a deploy script listens there. Webhooks in the repository settings (under Deploy keys) shows them. New webhooks are created on github.com.

  • Each row shows the address, the events it gets (All events or their names), Active or Inactive, and how the last delivery went (the answer code of the receiver, or why it failed).
  • Tap a webhook: Recent deliveries, Turn off / Turn on (an inactive webhook keeps its settings, GitHub just sends nothing), Send a ping (a test message, its result appears under Recent deliveries), Copy URL, Delete webhook and Open in browser.
  • Recent deliveries lists the last 50 messages GitHub sent, newest first: the event (e.g. push or issues.opened), the receiver's answer (green when it was accepted, red when it failed or GitHub could not connect), how long it took and when. Tap one for Details (the receiver's answer and the payload GitHub sent, with Copy payload) or Redeliver to send it again, e.g. after fixing the receiver; the new attempt appears at the top, marked Redelivery.

Security

Security in the repository menu (repositories you can push to) has the tabs of the Security page on github.com:

DependabotDependencies with a known vulnerability: package, vulnerable and patched versions, the advisory (CVE / GHSA).
Code scanningProblems that CodeQL or another scanner found in the code, with file and line.
Secret scanningTokens and keys that were committed, and in which file and commit. The secret itself is not shown.
SecretsAdmins only: the secrets of GitHub Actions, of Dependabot and of each environment.
VariablesAdmins only: the variables of GitHub Actions, of the repository and of each environment.
  • Alerts are colored by severity: critical red, high orange, medium amber. Show closed alerts in the menu shows fixed, dismissed and closed ones.
  • Tap an alert for its details. A Dependabot alert also shows, when GitHub knows them: Your version (the version or range your manifest or lockfile names), whether the package is a direct or transitive dependency and runtime or development only, the CVSS 4.0 and 3.x scores (out of 10, with their vectors), the EPSS chance that the flaw is exploited in the next 30 days, and reachability (whether your code calls the vulnerable part). Dismiss… (Dependabot, code scanning) or Close as… (secret scanning) asks for a reason and an optional comment; Reopen undoes it.
  • When a scanner is off, an admin gets Turn on (Dependabot alerts, secret scanning) or Set up CodeQL (code scanning; the first analysis runs in Actions and takes a few minutes). In private repositories some scanners need GitHub Advanced Security.
  • Admins: ⋮ → Security settings turns features on or off: Dependabot alerts, Dependabot security updates (pull requests that update vulnerable dependencies), Secret scanning, Push protection (blocks pushes that contain tokens) and Private vulnerability reporting. A switch that is grey is not offered for this repository (some need GitHub Advanced Security in private repositories).
  • A leaked token: revoke it where it was issued (e.g. github.com → Settings → Developer settings), then close the alert as Revoked. Deleting the file does not help, the token stays in the history.

Secrets for workflows

  • Workflows read them as ${{ secrets.NAME }}, e.g. a Telegram bot token or a signing key password.
  • The + button adds a secret: a name (letters, digits and _, stored in upper case, not starting with GITHUB_) and the value (up to 48 KB, several lines allowed).
  • Tap a secret for Update value or Delete.
  • The line at the top (Repository secrets (Actions) ▾) switches to Dependabot secrets (Dependabot uses them for private registries) or to an environment (e.g. production): only jobs that name that environment get its secrets. Environments are created on github.com under Settings → Environments.
  • OpenHub encrypts the value on the phone with the repository's public key, as GitHub requires; only GitHub Actions can read it. GitHub never shows a value again, not even to you, so keep your own copy.

Variables for workflows

  • Workflows read them as ${{ vars.NAME }}: settings that are not secret, e.g. a build type, a channel name or a server address.
  • Unlike secrets, values can be read: each one is shown under its name. Tap it for Edit variable (the name can change too), Copy value or Delete; + adds one. Names follow the rules of secrets.
  • The line at the top switches between the repository's variables and those of an environment.
  • Everyone who can see the workflow runs can read variables: put passwords and tokens in a secret.

Danger zone

careful Change visibility (public / private), archive or unarchive, transfer ownership, and delete the repository: you type its full name to confirm.

Delete needs a permissionDeleting needs delete_repo. If OpenHub says it is missing: with a token, open it on github.com (Settings → Developer settings → Personal access tokens), tick delete_repo and press Update token. Signed in with the browser? Log out and use Login with browser again; GitHub asks you to allow the new permission.
7 · new repository

New repository in the side menu works like github.com/new.

  1. Owner: your account, or one of your organizations (tap to switch).
  2. Repository name: OpenHub checks while you type whether it is still free. Letters, digits, -, _ and .; other characters become -.
  3. Description, then Public or Private.
  4. Initialize with a README, a .gitignore and a license, or leave them all off for an empty repository you can push to.
  5. Create repository: the new repository opens.

.gitignore

Lists files git should not track (build output, local settings). Search the templates and tick one or more (e.g. Android and Gradle), and add your own lines such as *.apk or local.properties. Everything is combined into one file.

8 · pull requests

A pull request (PR) proposes merging the changes of one branch into another, so they can be discussed and checked first. Open Pulls on the Info tab or Pull requests in the repository menu. Links to pull requests (notifications, issues, READMEs, other apps) open here too.

States

Open waiting   Draft not ready yet   Merged done   Closed closed without merging

Inside a pull request

ConversationThe description, comments, reviews and line comments, and the status of the checks (GitHub Actions and other CI).
CommitsThe commits it adds.
FilesThe changed files with the number of comments; tap one for its diff (9).

At the bottom: Comment and Review changes (Comment, Approve or Request changes), with Write and Preview like on the site.

The merge box

If you can write to the repository:

  • Merge pull request with any method the repository allows: merge commit, squash (all commits become one) or rebase, with your own title and message. GitHub runs the merge in the background and OpenHub waits for its answer: merged, added to the merge queue, or the reason it failed (a rule of the base branch, for example).
  • When the merge is blocked, the merge dialog offers Merge without waiting for the requirements (bypass rules). It works only if GitHub lets you bypass those rules (usually repository admins).
  • Ready for review for a draft, or Convert to draft.
  • Delete branch after merging or closing, and Restore branch if you change your mind.
  • Close pull request / Reopen pull request.

When GitHub blocks the merge, the box lists what the base branch asks for: the rules of its rulesets (with the ruleset's name) and, for admins, its classic branch protection. A pull request rule also shows how far you are, for example 1 of 2 approved, reviewers who asked for changes, and unresolved conversations when the rule wants them resolved.

The ⋮ menu has Edit (title, description), Refresh, Share, Copy URL and Open in browser. Long-press a comment to edit or delete your own.

Stacked pull requests

A stack is a chain of pull requests where each one builds on the branch of the one below it, so a big change can be reviewed in small parts. Stacks are made on github.com or with the GitHub CLI; OpenHub shows them:

  • The list marks a stacked pull request with Stack 2/4: its place in the stack, counted from the bottom.
  • Inside it, the Stack box under the title lists the whole stack, top first, down to the branch it merges into. Your pull request is marked; tap another one to open it.
  • A stack merges from the bottom up. Merging a pull request in the middle also merges the open ones below it, so the button says, for example, Merge 3 pull requests and the box names them. The ones above stay open and move onto the base branch.

Archived pull requests

People with triage access or higher can archive a pull request, for example spam: ⋮ Archive pull request. GitHub closes it, only people with triage access or higher can still see it, and its conversation becomes read-only. Open and closed pull requests can be archived, merged ones cannot. ⋮ Unarchive pull request makes it visible again; it stays closed until you reopen it.

Archived pull requests are in the Archived tab of the list and marked Archived in Closed. GitHub finds them with search, which can take a few seconds to catch up after a change.

No merge button?The box says why: conflicts (both branches changed the same lines; solve it on github.com or with git), a draft, failing required checks or missing approvals.

Opening a pull request

  1. Tap + in the pull request list.
  2. Base: where the changes go (usually main). Compare: where they come from.
  3. Check the summary (commits and files), write a title and a description.
  4. Tick Create as draft if it is not ready, then Create pull request.

In a fork, the pull request goes to the original repository by default. If the repository has only one branch, the screen says so and offers Branches; easier still, edit a file and commit to a new branch with Start a pull request (4).

9 · reviewing code line by line

In a pull request, Files → a file opens its diff:

+ green added lines   - red removed lines   @@ start of a changed block

  • Tap a line to comment on it.
  • Several lines: long-press the first line (it turns yellow), then tap the last one. Tap the same line again to cancel.
  • Suggest a change (on added or unchanged lines) puts the code into a suggestion block. Edit it, and whoever can push to the pull request's branch can apply it with one tap.
  • Applying suggestions: if you can push to the pull request's branch (your own repository, a fork that allows edits by maintainers, or your own fork), a suggested change in the diff screen has Commit suggestion and Add to batch. Commit suggestion asks for the commit message (Apply suggestion from code review by default) and commits it to the branch. Add to batch collects several (also from other files); the bar at the bottom shows how many, Commit applies them all in one commit and Clear empties the batch. The authors of the suggestions are credited with Co-authored-by, like on github.com.
  • Only suggestions on the current code can be applied (outdated ones have no buttons). If the lines or the branch changed meanwhile, nothing is written and the app asks you to reload.
  • Comments appear under their line, with Reply… to answer. Long-press one to edit, delete or copy its link.
  • Comments on code that changed since are listed at the top as outdated.

A review with several comments

Like on github.com, the comment window offers Add single comment (sent at once) or Start a review. A review collects comments first:

  1. Choose Start a review; later comments default to Add review comment.
  2. Reply… under a thread offers the same choice: a reply added to the review waits with a Pending badge in its thread and is sent together with the review.
  3. They show under their lines with Pending; only you see them. Long-press one to edit or delete it. They stay on the phone if you close the app. The phone draws them like github.com does: bare links, @user, #123 and owner/repo#123 become links, footnotes and common :emoji: codes work (the same in Preview when GitHub cannot be reached).
  4. Finish review in the bar at the bottom (or Finish review (n) on the Conversation tab): pick Comment, Approve or Request changes, add a summary if you like, and everything is sent as one review.

The menu has Discard pending review to throw the pending comments away.

Resolving conversations

Under a thread, Resolve conversation marks it as done; resolved threads fold into one line (tap it to show or hide them) and get a Resolved badge on the Conversation tab. Unresolve conversation opens it again. The pull request's author and people with write access can resolve.

Your own pull requestGitHub does not let you Approve or Request changes on your own pull request; comments are fine. A review of type Comment needs some text, unless it carries line comments.
10 · issues

Issues are bug reports, questions and requests. Open them from the Issues number on a repository's Info tab or from Issues in the side menu (yours: created, assigned, mentioned). These lists show only issues: GitHub counts pull requests as issues too, but they are under Pulls (a milestone's Issues and pull requests keeps both).

  • Create, edit, close and reopen issues.
  • Comment with a Markdown editor and preview.
  • Manage labels in your own repositories.

Templates

When a repository has issue templates (like Bug report or Feature request), a new issue starts with Choose a template. The template fills in the title, the text and, if you may set them, its labels and assignees. Issue forms become sections (### Question) to answer, checkboxes become a task list. Blank issue starts empty.

Pictures and videos

The paperclip, Attach image or video, uploads a picture (PNG, JPEG, GIF, WebP, SVG; up to 10 MB) or a video (MP4, MOV, WebM; up to 10 MB on GitHub's Free plan, 100 MB on paid plans) to GitHub and puts its link into the text, like dragging a file into the comment box on github.com. You find it in the bar above the Markdown editor (comments, the issue text, release notes), next to the editor button of a new or edited issue, and next to the Write and Preview tabs of the comment boxes in pull requests, line comments and discussions. GitHub shows a picture in the text and a video as a player.

  • GitHub lets apps attach files only to repositories you can write to. In other repositories the paperclip explains this and offers Open on github.com, where you attach the file by hand. The same button appears when GitHub refuses an upload, with GitHub's reason.
  • The file goes in as a paragraph of its own. GitHub keeps a new file private until the comment that uses it is sent, so Preview shows the picture from your phone.
  • An uploaded file stays on GitHub even if you do not send the comment, as on the website.
  • The select button next to the paperclip (in the comment boxes and in the Markdown editor) selects the whole text, to copy or replace it; tap it again and the text is cleared.
  • Every other text field (titles, names, search, branch, inputs) shows the same mark at its right end while you type in it: one tap selects the whole text, a second tap clears it.
  • Comments look as on github.com, pictures included, also in the list: quotes with a grey bar on the left, alerts (Note, Tip, Important, Warning, Caution) with GitHub's icon and a colored bar, tables, task lists and highlighted code. Tap a comment to read it alone. In pull requests and discussions a tap on a picture opens it. A code block has a copy button in its top right corner: tap it and the code is copied. The same button is on the code blocks of READMEs, wiki pages, release notes and Markdown files, and in the top right corner of a code file (it copies the whole file). Tap a table to open it on its own page, where a wide table scrolls sideways. A folded section (▸ Details) is closed as on github.com: tap its line to open it (▾) and again to close it; that tap does not open the comment. When pictures are switched off on mobile data (Settings), a picture shows as [its name] and an emoji picture of GitHub by its name, e.g. :octocat:.
  • Long-press a comment for Quote reply (a new comment with that comment quoted, as on github.com), Mention @name (a new comment that starts with the author's name), Share or Copy URL, and Edit and Delete on your own comments. The same works in pull requests (a line comment is answered in its thread on the diff page), discussions (the answer goes into that comment's thread) and gists.
  • In pull requests and discussions a video shows as ▶ Play video under its file name: tap it and it plays in the app. In Preview and in a comment opened alone, tap the video or its link and it plays in the app. A video you attached a moment ago plays from your phone. A bare link to a picture opens the picture. If the phone cannot play a video, Open in browser is offered.

Sub-issues

A big issue can be split into sub-issues. An issue with sub-issues shows a box under its text: Sub-issues: 2 of 5 done with a bar (GitHub's own count), then the sub-issues in GitHub's order with their state (open, Closed, Not planned). A sub-issue shows Sub-issue of with its parent. Tap any of them to open it. In the issue list, Sub-issues 2/5 appears next to the number.

  • With triage or write access to the repository, the box is shown on every issue and has Add sub-issue: Add an existing issue lists the open issues (search by number or title; a number that is not in the list is looked up on GitHub first (a pull request, a missing issue or a closed issue is shown as such); type owner/repo#12 or paste a link for an issue of another repository of the same owner, or a closed one), Create a new sub-issue opens the issue editor and adds the new issue.
  • An issue that already has a parent is marked (has a parent); adding it asks first and then moves it here (Move here).
  • Long-press a sub-issue for Move up, Move down and Remove sub-issue. Removing only takes it out of the list; the issue itself stays.
  • Closing or reopening a sub-issue updates the parent's count when you go back to it.

Blocked by, blocking and related issues

Under the sub-issues an issue shows its relationships: Blocked by (with how many of them are still open), Blocking and Relates to, each issue with its state; tap one to open it. In the issue list, Blocked by 1 appears next to the number while a blocking issue is open.

  • With triage or write access: Add relationship → Blocked by…, Blocking… or Relates to…, then pick the issue the same way as a sub-issue (list, number, owner/repo#12 or a link).
  • Long-press an issue in one of these lists: Remove relationship asks, Remove removes it. Only the link goes; both issues stay as they are.
  • "Blocking" is the same link seen from the other side: if #7 blocks #10, #10 shows #7 under Blocked by.

Issue types and fields

Organizations can give their issues a type (like Bug, Feature or Task) and their own fields (like Priority or a start date). Both are set up by the organization on github.com, so personal repositories have none. An issue with a type or field values shows a Type and fields box under its text, with GitHub's colors; the issue lists show the type before the number.

  • With write access to the repository, the box lists the type and every field of the organization, empty ones as None. Tap a row to change it: Issue type offers the organization's types and No type; a text or number field opens a text box, a date field a calendar, a choice field its options (several for a multiple choice). Remove clears a value.
  • The box always shows what GitHub has saved: if GitHub does not change the type, the app says so.

Milestones

Repository menu → Milestones: Open / Closed, sorted by due date. Each shows its due date (red when it is past), a bar with how many of its issues and pull requests are closed, and its description.

  • Tap a milestone → Issues and pull requests lists them (Open and Closed tabs), or Open in browser.
  • If you can push to the repository: + creates one (title, optional description and due date), and the menu of a milestone has Edit milestone, Close milestone / Reopen milestone and Delete. Deleting keeps the issues; they just lose the milestone.
  • An issue gets its milestone in the issue editor (row Milestone).

Discussions

Repository menu → Discussions (only shown when the repository uses them). Open / Closed, the filter icon picks one Category, Answered marks questions with an accepted answer.

  • Open a discussion to read the post, the comments and their replies. The comment button writes a new comment; Reply… answers a comment.
  • ▲ 3 upvotes (tap again to take it back). In question categories the author and maintainers can Mark as answer; the answer gets a badge.
  • Long-press a comment to edit or delete your own, or to copy its link or text.
  • Images in posts and comments are shown (screenshots pasted on github.com too). The same goes for pull request comments.
  • Polls appear under the post. Tap an option to vote; a vote cannot be changed afterwards. Once you have voted (or when you cannot vote) the results show with a bar per option and your choice marked with ✓. Polls themselves can only be created on github.com.
  • ⋮ → Close discussion… closes it as Resolved, Outdated or Duplicate (the author and maintainers); Reopen discussion opens it again. The reason shows next to the category.
  • + in the list starts a new discussion: pick the category, a title and the post.
  • Discussion links from other apps and from notifications open here too.

Labels, assignees and milestone

If you have triage or write access to the repository, the issue editor has Labels, Assignees (up to 10) and Milestone (an open milestone, or No milestone). The issue shows its assignees and milestone under the labels.

11 · releases, tags and downloads

A release is a published version of a project, usually with files to download (APKs, zip modules, binaries).

Latest newest stable   Pre-release test version   Draft not published (only people with write access see it)

  • Open a release for its notes and files (assets) with size and download count. Tap a file to download it, long-press to copy its link. The download button also offers the source code archives.
  • Downloads go to the phone's Download folder. The built-in downloader works on Wi-Fi, mobile data, roaming and VPN, and resumes after a lost connection.
  • Checked downloads: GitHub keeps a SHA-256 checksum of every release file. The built-in downloader compares the downloaded file with it and says SHA-256 verified. A file that does not match (damaged or replaced on the way) is deleted and the download is reported as failed. Long-press a release file to copy its link or its SHA-256. Files uploaded before June 2025 and source code archives have no checksum.
  • When a download finishes, its notification has Install (APK files) or Open, and Share, e.g. to send a module zip to your root manager.

Releases of your starred repositories

Releases in the side menu lists the newest release of every repository you starred, newest first, grouped into Today, This week, This month and Older.

  • New marks releases published since your last visit; the title bar counts them. Mark all as seen in the menu clears them.
  • Tap a release to open it, the download button for its files and source code, the avatar for the repository. Long-press for Open repository, Download, Open in browser and Share.
  • Filter repositories narrows the list by name. Show pre-releases in the menu (on by default) shows a newer test version instead of the latest stable one.
  • The last list opens at once; pull down or tap Refresh to load it again.

Tags

A tag is a name for one commit, usually a version such as v1.2.0; every release is made from a tag. Tags in the repository menu (also in the menu of the releases list) shows all of them, the newest commit first, like the tags page of github.com.

  • Each row shows the tag name, the short commit SHA with the commit's first line (or the tag's own message), when it was made, Annotated for a tag with its own message and author, and the release made from it: Latest release, Release, Pre-release or Draft release. The line at the top counts the tags.
  • Find a tag by name asks GitHub for the tags whose name matches what you type. Load more tags loads the next 50.
  • Tap a tag: Open the release, or Create a release from this tag when it has none (people with write access; the release editor opens with the tag filled in), Browse files (the files as they were at this tag), Open the commit, Compare with the tag below it (what changed between two versions; only without a search), Download source code (zip) or (tar.gz), Copy tag name, Delete tag and Open in browser.
  • Delete tag (people with write access) removes only the name; the commit stays. When a release is made from the tag, the question says so: to remove a published release and its tag together, open the release, tap Delete release and tick Also delete the tag. A draft release is not deleted with its tag. The tag of an immutable release cannot be deleted, and rulesets can protect tags too; then GitHub refuses and the app shows its reason. After a delete the list is read from GitHub again.
12 · publishing releases

In repositories where you can write, releases are managed like on github.com.

  1. + in the releases list: New release.
  2. Tag: pick one with the tag button or type a new one such as v1.2.0; a new tag is created from the Target branch when the release is published.
  3. Title and notes. Generate release notes lets GitHub write them from the merged pull requests. Write / Preview shows how they will look.
  4. Add files: an APK or a zip you built, e.g. in Termux (it appears in the file picker's side menu). The pencil renames a file, the cross removes it.
  5. Save draft keeps it private, Publish release makes it public.
Safe uploadsWith new files the release stays a draft while they upload and is published only when every file arrived, so nobody downloads half a release. Uploads run in the background with a progress notification and Cancel; a lost connection is retried.

From other apps

Share files from a file manager, Termux (termux-share) or Telegram and choose Upload to GitHub. Pick the repository (the last one is on top), then:

  • New release or an existing release: the files are added to it. Files that already exist can be replaced.
  • Add to the repository files: type a folder (empty for the top folder; the last one is remembered) and the files are committed there, to the default branch or, in the commit dialog, to a new branch with a pull request. Files that already exist in the folder can be replaced.

In an open release

The menu has Edit, Publish release (drafts), Set as latest release, Upload files, Update SHA256SUMS and Delete release (optionally with its tag). Each file has a pencil to rename it and a menu to copy its link or delete it.

SHA256SUMS: tick Add a SHA256SUMS file under the files of a release (the choice is remembered) and, after the uploads, the release gets a file named SHA256SUMS with the checksum of every file, in the format of sha256sum, so anyone can check a download with sha256sum -c SHA256SUMS. The checksums are the ones GitHub keeps for each file, so nothing is hashed on the phone. A release that already has the file keeps it up to date when you upload more files; Update SHA256SUMS in the menu writes it again at any time. Files uploaded before June 2025 have no checksum on GitHub and are left out.

Clean up old releases (⋮ on the release list of a repository you can write to) deletes all but the newest releases at once: keep only the newest one, or the 3 or 5 newest, optionally with their tags and with drafts. The release marked Latest is always kept, and you see the list of what goes before anything is deleted.

13 · github actions

Many projects build their apps automatically with GitHub Actions, and the newest test builds are often only there. Repository menu → Actions.

Success Failed In progress Queued Cancelled Skipped

  • Each row is one run: what started it, the workflow, its number, the branch and the status.
  • Tap a run to open it: status and duration, every job with its steps (the failed step in red) and the artifacts (the files it built; tap one to download it as a zip). GitHub deletes artifacts after a while (usually 90 days); old ones show expired. A run that is still going updates itself every few seconds: a moving bar at the top, pulsing dots and running timers show what is going on, and the step that runs now is bold (also in the status line).
  • Long-press a run to open it in the browser.
  • The filter icon shows one workflow; the menu has Successful runs only.
  • In your own repositories the play button starts a workflow by hand: pick it, check the branch, add inputs as key=value lines. Only workflows with a workflow_dispatch trigger can be started. The new run opens right away and updates itself while it runs.

Logs, re-run and cancel

  • Tap a job (or Log) for its log. Groups are folded like on github.com (tap to open; groups with an error are open), errors are red and warnings amber. The menu has Find / Find next, Next error, Expand all, Go to the end and Download log (the whole file, also for very long logs, of which the screen shows the last 100,000 lines). While a job runs, the log shows what GitHub has so far (or a note, if it has nothing yet) and loads again when the job has finished.
  • Menu of a finished run: Re-run all jobs or Re-run failed jobs; long-press a job for Re-run this job. Tick Enable debug logging for more detailed logs. You get a notification when the re-run finishes.
  • Menu of a running run: Cancel run, and Force cancel when a normal cancel does not end it. GitHub needs a minute or two to stop the jobs; until then the run shows Cancelling….
  • Links to runs and jobs (from notifications, Telegram, issues) open here too.
  • Artifact to a release: tap an artifact (the arrow downloads it right away) → Add to a release…. OpenHub downloads and unpacks it, you tick the files you want (e.g. the AnyKernel zip and boot.img), and the upload screen opens for this repository: choose a release or New release, or commit the files to the repository instead.

Workflows and caches

  • Menu → Workflows: every workflow of the repository with its state as GitHub reports it: Active, Disabled, Disabled: no activity in the repository for 60 days (GitHub stops scheduled workflows of quiet public repositories), Disabled in this fork or Deleted (the file is gone, its old runs remain).
  • Tap a workflow: Show runs (back to the runs, filtered by it), Disable workflow or Enable workflow, Open the workflow file, Open in browser. A disabled workflow does not start at all (no pushes, pull requests, schedules or play button) until you enable it again; its file and old runs stay. After the change OpenHub asks GitHub again and shows the real new state.
  • Menu → Caches (or the Caches tab): the dependency caches that workflows saved with actions/cache and similar steps: key, branch, size, last use. The line at the top is GitHub's own count, which it updates about every 5 minutes. The menu sorts them (Last used, Size, Created).
  • Tap a cache: Copy key or Delete cache; the menu has Delete all caches…, which first counts them on GitHub and asks. Useful when a broken cache makes builds fail, or to free the space. The next run builds a deleted cache again (once a bit slower).
  • Enabling, disabling and deleting need write access to the repository; everyone else sees the lists only.

Notifications when a run finishes

  • Start a workflow with the play button and leave the app: when the run ends you get a notification (succeeded, failed or cancelled), with the branch and how long it took.
  • Menu → Notify when runs finish: the same for every run of this repository, also runs started by a push, a pull request or a schedule. Tap it again to switch it off.
  • A successful run with one or two artifacts gets Download buttons right in the notification; with more, the button opens the run. Tapping the notification opens the run (jobs, logs, artifacts).
How fastThe repositories are checked every 15 minutes. While a run is going (or one you started has not finished yet), OpenHub checks every 90 seconds, so the notification comes about a minute after the end.

20 · problems and answers

"Must have admin rights" when deleting a repository

The delete_repo permission is missing; see 6.

Changing a workflow file is refused

The workflow permission is missing. Create a new token with Create token, or log in with the browser again.

No Merge button

Read the merge box: conflicts, a draft, missing approvals or failing checks. When the merge is blocked it lists the rules of the base branch and what is still missing. Conflicts are solved on github.com or with git.

Create pull request stays grey

Base and compare are the same branch, or the compare branch has no new commits. Commit something to that branch first.

A github.com link opens the browser

Allow github.com links once; see 19.

Phone notifications do not come

Check that GitHub notifications is on and Android allows OpenHub's notifications. On some phones (Xiaomi, Samsung) set the battery setting of OpenHub to No restrictions, or background checks may be delayed.

Stargazers or watchers are empty

GitHub shows them only to owners and collaborators since July 2026.

A page shows old data

Pull the page down to load it again. Every page that shows GitHub data can be pulled: lists, the Info and Files tabs of a repository, profiles, files, branches, releases, all three tabs of a pull request, its line diff, discussions, milestones, Compare, code search and job logs. A pull always asks GitHub again instead of showing saved data. Some pages also have Refresh in the menu. With Cache Controller on, saved data appears first and is then updated. The lists of the side menu also update themselves (see 2).

News shows someone I do not follow

News is GitHub's feed of the people you follow and keeps events up to 90 days, also of people you stopped following or of deleted accounts (their profile then shows "Page not found"). They disappear from the feed by themselves.

A download failed with "SHA-256 does not match"

The file that arrived is not the one on GitHub (damaged on the way, or replaced by something on the network). It was deleted; download it again, if possible over another network.

22 · privacy and security

OpenHub talks only to GitHub. There are no ads, no analytics and no servers of its own.

  • Your token is stored only on this phone, encrypted with a key of the Android Keystore that never leaves the phone. It is sent only to GitHub's API (api.github.com), never to other addresses, file links or web pages.
  • Backups: your accounts and tokens are never part of a phone backup or a transfer to a new phone; settings are. On a new phone you sign in again.
  • Browser sign-in is protected against other apps: it only accepts the answer to a sign-in started in OpenHub (state check and PKCE).
  • Short-lived browser sign-in: a browser sign-in gets a token that works for 8 hours, plus a refresh token (about 6 months) that OpenHub uses to get a new pair by itself shortly before the token ends. A stolen token is useless after a few hours. Both are encrypted like the token. Without a connection nothing changes; OpenHub simply tries again later. Signed in with the browser before 3.11.0? Your sign-in keeps working as it is; sign in again with the browser to get the short-lived kind. If GitHub stops accepting the refresh token (unused for about 6 months, or you revoked OpenHub on github.com), the account stays on the phone: OpenHub asks you to Sign in again, or shows one notification when it finds out in the background. Until then the background checks of that account only look at public data.
  • Log out removes the token and the saved GitHub pages from the phone. A browser sign-in is also revoked at GitHub (only the one of this phone: OpenHub on your other devices stays signed in). A personal access token keeps working until you delete it on github.com: Settings → Developer settings → Personal access tokens.
  • Fewer rights: Create token ticks everything OpenHub can use. Untick delete_repo if you never delete repositories in the app, or workflow if you never edit workflow files; the rest keeps working.
  • Encrypted connections only, checked against the phone's system certificates. Certificates added by the user or by other apps are not trusted, so a proxy on the network cannot read your token. On Android 17 and newer the phone also checks that GitHub's certificates are publicly logged (Certificate Transparency) and, when GitHub's servers support it, hides the server name from the network (Encrypted Client Hello).
  • Sharing to OpenHub accepts files that other apps share; it never uploads OpenHub's own private files, whatever another app asks.
  • No connection at start? Your account stays; OpenHub offers to try again.
  • Your account is never removed by itself. When GitHub no longer accepts a sign-in (the token was revoked, or a short-lived sign-in could not be renewed), OpenHub asks you to Sign in again and suggests the same account on GitHub's page; until then the account stays on the phone. Only Log out removes it.

You can see and revoke app access any time on github.com: Settings → Applications. This help page loads nothing from the internet.
